# FieldSignal V0 interface contract

Current contract: 2026-10-23. All paths begin `/api/v1`; JSON uses snake_case. API errors return `{error: {code, message, details}}`. All datetimes are ISO 8601 with timezone, normalized to UTC. Growing-season date membership uses Asia/Shanghai civil dates (July 1 to the following June 30); farm-event dates use the same agronomic calendar. Local prototype only, bound to 127.0.0.1. No account system or remote deployment is included. Data is empty by default.

## Entities

- Parcel: `id, name, region, crop, season, sowing_date?, cultivar?, geometry, area_ha, area_method, boundary_source, boundary_reference?, boundary_crs, data_origin, created_at`. `region`: `shayang|luotian|other`; `crop`: `oilseed_rape`. `geometry`: GeoJSON Polygon WGS84 closed ring (no holes in V0). `data_origin`: `user|fixture`; fixture parcels cannot accept actual observations.
- Observation: `id, parcel_id, observed_at, source, source_record_id, features, quality, provenance, data_origin, ingested_at, created_at`. `source`: `sentinel2|sentinel1|weather|manual`. Features support `ndvi, ndre, evi, ndwi, vv_db, vh_db, temperature_min_c, temperature_max_c, precipitation_mm`. Quality: `usable, valid_fraction, cloud_fraction?, flags: string[]`. Provenance: `provider, collection, item_id, processing_version, license?, source_uri?, spatial_resolution_m?, temporal_support, support_note?`. Local pre-cropped S2 TIFF/STAC and POWER JSON normalization is now supported by a separate reusable adapter; there is no automatic download or general raster-upload endpoint.
- AnalysisRun: `id, parcel_id, method, model_version, evaluated_at, status, risk_id, observation_count, message, data_origin, created_at, mode, qualification_status, monitoring_eligible, qualification_reasons, preview_status, preview_evidence`. New user runs have `mode=preview`, `status=preview_only|blocked`, `risk_id=null`, and `monitoring_eligible=false`. `preview_status` is `insufficient_data|stale|not_flagged|candidate`; `preview_only` covers the last two, `blocked` the first two. `preview_evidence` contains the candidate evidence or null. Fixture runs have `mode=fixture_demo`, their original four algorithm statuses, nullable synthetic `risk_id`, and null preview fields. Qualification is `unverified|declared_only|fixture_demo`; no current run is qualified for formal monitoring. `not_flagged` is never a healthy diagnosis. Historical runs may omit the new fields; see compatibility below.
- RiskCandidate: `id, parcel_id, observation_id, method, status, disposition, mode, monitoring_eligible, priority, summary, evidence, model_version, data_origin, created_at`, with optional latest `verification_id` and historical `legacy_status`. Current read status: `open|assigned|review_required`; disposition is `unresolved`. Reads label all existing user candidates `mode=preview` and synthetic candidates `mode=fixture_demo`, with `monitoring_eligible=false`. Existing work is retained, not promoted to formal monitoring. Priority: `high|medium`; evidence includes source observation IDs, `metric, latest_value, baseline_median, baseline_mad, absolute_drop, score, baseline_count, limitations`.
- Visit: `id, parcel_id, risk_id?, source_verification_id?, status, due_date, assignee?, note?, plan_revision?, plan_updated_at?, data_origin, created_at`. Status: `pending|completed`; a received field report completes execution, not its event. A follow-up preserves `source_verification_id` and inherits its event's `risk_id` when one exists; the two links are compatible. Routine/unlinked visits may have null `risk_id`; ordinary visits omit the source field.
- Verification: `id, visit_id, parcel_id, observed_at, label, note, photo_ids, client_submission_id?, label_source, disposition, risk_id, source_verification_id?, data_origin, created_at`. Label: `normal|waterlogging|frost|disease_suspected|other|uncertain`. Every submitted label remains `label_source=field_report_unadjudicated`, `disposition=review_required`, including normal, uncertain and disease-suspected reports. This is neither diagnosis nor event resolution. Reports preserve the candidate and follow-up source links where applicable. Photo IDs must reference photos stored locally for this same visit. A photo is optional but absence must be visible.
- FarmEvent: `id, parcel_id, occurred_on, kind, note, created_at`. Kind: `sowing|fertilizing|spraying|drainage|other`.

## API

- GET `/health` → `{status, version, storage, demo_enabled}`
- GET `/dashboard` → `{parcel_count, open_risk_count, pending_visit_count, verification_count, review_required_count, parcels, recent_verifications}`. Each parcel adds `latest_observed_at, observation_count, data_status, open_risk_count, review_required_count, latest_optical_observed_at, optical_data_status, latest_weather_observed_at, weather_data_status, monitoring_status, qualification_status, monitoring_eligible`. Freshness statuses: `missing|stale|available|quality_limited`; timestamps are nullable and refer to the latest quality-eligible record of that modality. Legacy `data_status`/`latest_observed_at` are optical-only aliases. Weather does not renew NDVI freshness. `monitoring_status=preview_only|blocked|fixture_demo` is separate from freshness; `monitoring_eligible=false`. Open-risk counts include all unresolved candidates, even after reports; review counts count unadjudicated reports, including unlinked reports, not distinct events. Counts include explicitly seeded fixtures if present; they are not counts of qualified production alerts. Available never means healthy or formally qualified.
- GET `/parcels` → Parcel[]
- POST `/parcels` body `{name, region, season, geometry, sowing_date?, cultivar?}` → Parcel
- GET `/parcels/{id}` → Parcel
- GET `/parcels/{id}/observations` → Observation[] sorted oldest first
- POST `/parcels/{id}/observations` body `{observed_at, source, source_record_id, features, quality, provenance}` → Observation. `id`, `parcel_id`, `data_origin`, `ingested_at` and `created_at` are response-only fields.
- POST `/parcels/{id}/observation-batches` body `{schema_version: 1, bundle_id, scope: "parcel", bundle_sha256, processing_version, observations: ObservationCreate[], limitations: string[]}` → 201 `{id, parcel_id, bundle_id, bundle_sha256, processing_version, created_at, created_count, existing_count, observations: [{id, source, source_record_id, observed_at, status: "created"|"existing"}]}`. Max 500 rows and 1 MiB actual request bytes; all-or-none transaction. Same source/key with identical normalized content reuses the existing observation; different content returns 409 `observation_content_conflict`; repeated keys within one batch are rejected. All records must preserve the same parcel geometry and processing version; public samples, fixture targets, wrong season/geometry/mask are rejected. The declared manifest hash is not authenticated. Optional globally scoped `Idempotency-Key` durably replays the original receipt; changing key/content/target rules match other receipt-backed creates. A new key or no key can yield a new receipt with all rows `existing`, never duplicate observations. No automatic analysis or external transfer.
- POST `/parcels/{id}/analyses` body `{method?: "statistical"|"isolation_forest"}` → AnalysisRun. User-imported observations are evaluated only as exploratory preview; even complete hash/binding declarations cannot create a risk or visit. Missing, stale, quality-limited or insufficient-history input returns a blocked preview with its underlying reason. Explicit fixture parcels can produce labelled synthetic candidates. The client cannot submit mode, qualification or eligibility fields. Repeated analyses create run history, but candidate uniqueness prevents duplicate synthetic events.
- GET `/parcels/{id}/analyses` → AnalysisRun[]
- GET `/risks` → RiskCandidate[]
- POST `/visits` body `{parcel_id, risk_id?, due_date, assignee?, note?}` → Visit. Omitted/null `risk_id` creates a routine manual visit without a candidate; a linked risk must belong to the parcel and have no pending ordinary or source-linked visit (otherwise 422/409 `duplicate_visit`). Historical null-risk follow-ups are included through their source chain. A previous report, including legacy `verified`, does not prohibit an explicit later visit because the event is still unresolved. Creating a linked visit sets `status=assigned`, `disposition=unresolved`. `due_date` is a planning date and need not fall within the parcel season; actual report time must. Supports optional `Idempotency-Key` as below.
- GET `/visits` → Visit[]
- POST `/visits/{id}/plan` body `{expected_revision, due_date, assignee?}` → Visit. 仅更正待巡田任务的日期与执行人；旧任务版本视为0。事务内检查状态与计划版本，成功版本加1；已完成或旧版本返回409，地块/候选/核查提示/照片不变。支持同一全局 `Idempotency-Key` 绑定操作、任务及内容；相同更新重试在计划仍未被后续更新时返回200原结果，否则409并要求重读。前端只在当前表单保留请求编号，冲突不自动覆盖；不发送执行人通知。
- POST `/visits/{id}/photos` raw `image/jpeg|image/png|image/webp`, max 10 MB → `{id, visit_id, content_type, size_bytes, created_at}`. No outbound transfer; strips metadata by decoding/re-encoding.
- DELETE `/visits/{visit_id}/photos/{photo_id}` → 204, idempotently removes a same-visit staged photo while the visit is pending. Completed evidence is immutable through this route. Offline clients persist a delete queue and drain it before replacement uploads.
- GET `/photos/{id}` → local image bytes
- POST `/visits/{id}/verifications` body `{observed_at, label, note, photo_ids?: [], client_submission_id?}` → Verification. Atomically completes only the visit, stores an unadjudicated report, confirms selected photos, and marks any linked candidate `review_required` / `unresolved` with the latest report ID. It never resolves or dismisses the event, regardless of label or photo presence. Same client_submission_id + identical content replays the original success; conflicting reuse or a different completion returns 409.
- GET `/verifications` → Verification[]
- POST `/verifications/{id}/follow-up-visits` body `{due_date, assignee?, note?}` → Visit (201). Explicitly schedules a follow-up to a saved report. The server derives parcel, data origin and any candidate link from the source chain; submitted parcel/risk/source IDs or other extra fields are rejected. Stores immutable `source_verification_id`, inherited nullable `risk_id`, pending status and initial plan revision 0. Original reports/photos remain unchanged; an associated candidate becomes assigned but unresolved. One pending follow-up is permitted per report chain (`duplicate_follow_up_visit`); one pending ordinary or follow-up visit is permitted across the same candidate (`duplicate_visit`). This prevents branching from older reports while a descendant is pending, even without a candidate. Once the outstanding visit completes, an explicit request may schedule a later one. Missing source is 404; inconsistent identities, event links or cycles are 422 `invalid_follow_up_source`. Same global optional `Idempotency-Key` uses distinct operation `create_follow_up_visit` and the source report as target; exact replay returns the original creation snapshot even after plan changes/completion. A key reused for another source, operation or body is 409. Existing `/visits` request defaults and historical receipt bytes are unchanged. Follow-up report time cannot predate its source report (422 `verification_before_source`) or associated trigger (`verification_before_observation`); season/future-time checks still apply. Plan edits and completion preserve the source/event links.
- POST `/parcels/{id}/events` body `{occurred_on, kind, note}` → FarmEvent
- GET `/parcels/{id}/events` → FarmEvent[]
- POST `/dev/fixtures` → `{created: bool, parcel_id}` only if `FIELDSIGNAL_ENABLE_FIXTURES=1`. Inserts one conspicuously named synthetic parcel + simulated optical history. No fake true labels. Does not overwrite real data.

## 地块、农事与巡田请求重试

POST `/parcels`、POST `/parcels/{id}/events` 与 POST `/visits` 支持可选 `Idempotency-Key`：1–128 位 ASCII 字母、数字或 `._:-`，区分大小写；重复请求头返回422。同一数据库中编号全局唯一，并绑定请求类型、目标地块及校验/默认值归一后的内容。相同请求重试返回原来的 201 和记录；同编号换内容、类型或地块返回 409 `idempotency_conflict`。记录与回执在同一 SQLite 事务提交，并发及服务重启后仍可核对。巡田回执还绑定候选、计划日期、负责人和备注，与关联候选的 assigned 状态更新一起提交；即使任务随后已完成、候选进入待复核，重试仍返回创建时的原始回执，当前状态以 GET 列表为准。无此请求头的旧客户端保持原行为；无关联候选的普通巡田重复请求会创建独立任务；不自动去重历史数据；回执无自动过期，会随使用占用本地数据库空间。

前端编号仅保留在当前打开的地块/农事/巡田表单。相同已提交内容复用编号，改为新内容使用新编号；改回先前提交的内容仍复用原编号。关闭、重开或刷新页面后不保证识别此前请求。响应中断时原记录可能已保存，应保持内容重试核对，改内容或重开前先检查列表。此机制不新增离线农事或建任务草稿、自动提交。

前端不会仅凭 2xx 状态码确认保存。除明确的暂存照片 DELETE 204 外，成功响应必须是可读取的 JSON 对象或集合；地块、建任务、计划更新和农事回执还需核对记录身份、含时区保存时间及本次提交的字段。分析回执须核对请求地块、方法、来源与预览/模拟状态的一致性；单条观测回执须核对本次完整来源、时间、特征及质量内容。计划更新依据打开表单时捕获的原任务核对地块、候选、原提示及创建时间，并要求版本加1，不用刷新后的缓存作为旧请求依据。新任务回放仍为创建时快照，不插入当前任务列表。空/截断/HTML 回包、缺字段、错目标或不同内容均视为结果不确定，保留输入与原编号供手动原样重试，不自动关闭或报告成功。提交期间锁定输入，取消仍沿旧会话隔离处理。

## 监测资格与历史兼容（2026-10-23）

`unverified` 表示光学来源/绑定声明不完整；`declared_only` 仅表示每条光学记录的 parcel 用途、当前边界摘要、掩膜到资产摘要绑定、空间支持及像元质量计数声明完整且内部一致。二者都不等于已核实来源、真实掩膜覆盖或油菜类别，`qualification_reasons` 始终保留 `source_not_verified`。没有当前生产接入可以授予正式监测资格；所需来源核实与实际地块/掩膜/质量证据尚未实现，不以用户填写的 verified 标志替代。`fixture_demo` 仅是开发模拟演示，也不具备正式资格。详细边界见[本地导入契约](local-observation-import.md)。

本增量不迁移或批量重写旧数据库，SQLite schema version 保持3。旧候选 `verified` 只读映射为 `review_required` 并附 `legacy_status=verified`，因为原状态仅表示收到了报告。旧报告读取补上待复核语义，旧复查读取沿来源链恢复候选关联；保存字节与原始幂等回执不变。旧分析记录保留原字段/状态/说明作为历史事实，客户端须按地块来源将缺少 mode 的记录标为历史探索或模拟结果，不能据此声称具备正式监测依据。

旧复查的创建回执可能仍为 `risk_id=null`，而当前读取已恢复非空候选关联。若客户端无法核对这份旧快照，应保留输入并刷新检查，不补造回执、不自动换编号重提。历史重复待办不自动合并或删除；新增操作会考虑已有来源链阻止重复。损坏或循环的来源链返回结构化错误，不猜测关联、不静默丢弃数据。所有现场报告均待复核，包括无候选报告；本增量没有专业裁定、排除或事件解决提交入口，不把暂不能判断或正常报告当成闭环完成。

## UI

- `/` or `/admin`: management page, region/parcel selection, local boundary map (no external tiles), provenance + quality + history, analysis action, candidate → create visit, routine manual visit entry, verification list, parcel create (paste/local GeoJSON file, one-boundary preview), observation JSON input (developer/import workflow).
- `/field`: distinct phone-first workflow, pending visit priorities, parcel summary/trend, routine manual visit entry, camera/gallery attachment + observed label + note form, farm event form. Routine and candidate-linked visits show distinct source labels; forms retain the chosen parcel and show its season. Bottom navigation: 巡田 / 地块 / 记录. Browser-based mobile prototype, not yet a native app, offline sync or notifications.
- Always show no observations as `待接入数据`; expired as `数据已过期`; synthetic as `开发模拟数据`. User field locations/photos stay local. No external map or telemetry calls.

Parcel files accept Polygon, Feature or a FeatureCollection with exactly one Polygon Feature, up to 1 MiB. Coordinates are not repaired or transformed; holes, Z positions and CRS declarations are rejected. Feature properties do not prefill other fields; optional bbox is ignored and preview bounds come from coordinates. Only explicit Save sends the boundary to the local service, which still validates topology and area.

Boundary source defaults to user_provided; user_survey/public_dataset describe the submitted provenance rather than verified ownership. Synthetic fixtures override the source to synthetic_fixture. Area is a local estimate, not a surveying result. Observation ingestion time is separate from acquisition time. Temporal support defaults to instantaneous; daily UTC/local-solar/Beijing intervals must remain distinguishable.

Photo lifecycle: upload creates staged bytes; successful verification atomically confirms only selected photo IDs and removes other staged uploads for that visit. Client drafts remain until the acknowledged submission version is safely cleared. Verification date must fall in the parcel season and, for a linked candidate, be no earlier than the triggering observation. Historic seasons and later-entered genuine historic records remain supported.

## 2026-10-16 local-source extension

See [local observation import contract](local-observation-import.md) for provenance fields, the manifest schema, generic CLI, public-sample API and isolation. GET `/sources` is read-only; POST `/source-imports/public-sample` explicitly imports a bundled public sample without any parcel ID. Existing field observation imports reject public-sample scope and enforce declared parcel geometry hashes when usage_scope=parcel. Old provenance remains valid with usage_scope=unverified. Source_imports are separate from all farm tables and retain immutable input/processing/time evidence.


## 提交前 UI 核对（2026-10-20）

现场编辑第一次提交仅进入只读核对，不发送 API 请求；用户明确确认后才沿原流程进行时间与本机保存检查、暂存照片处理和核查提交。返回修改不新建提交编号。核对失效、存储失败或未知提交结果不自动重试；重新核对后继续同一草稿的幂等规则。该提交前核对本身不允许修改已提交核查；当前服务端状态以本契约的“报告收到、事件仍待复核”规则为准。
